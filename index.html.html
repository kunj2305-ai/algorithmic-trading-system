01Abstract

This project designs, validates and deploys a fully automated trading system for options on the NIFTY 50 index. The system ingests market data from a broker API, generates directional signals from a volatility-adaptive trend indicator, selects a tradable option contract using a Black–Scholes pricing model, and manages the complete order lifecycle without human intervention.

The engineering contribution is a fault-tolerant, stateful service that operates unattended during market hours, including two independent strategy engines that share a single broker account and must therefore reconcile their positions without interfering with one another. The research contribution is a rigorous, cost-honest evaluation methodology: every result is charged the full real-world transaction cost, validated against an independent platform, and subjected to falsification tests designed to reject the hypothesis rather than confirm it.

Over 6.5 years of historical data the primary strategy produces a profit factor of 2.08 across 735 trades with a maximum drawdown of 3.0% of peak equity. A dedicated study (Section 11) then answers a question that pure backtesting cannot: which option contract should actually be bought to express the signal. Pricing every historical trade against live-recorded market depth, the study demonstrates that at-the-money options retain only 34% of the strategy's theoretical edge against 78% for deep in-the-money contracts — a difference of ₹12 lakh over the test period that no price-only backtest would have revealed. Section 13 documents a result that was withdrawn after its underlying assumption failed verification.

02Problem & Motivation

Discretionary trading suffers from well-documented cognitive failures: inconsistent rule application, loss aversion, and an inability to monitor markets continuously. An algorithmic system replaces judgement with a deterministic specification — but doing so honestly is substantially harder than it first appears, and this is where most retail systems fail.

Three problems define the project's scope:

  1. The validation problem. A strategy tested carelessly will almost always appear profitable. Look-ahead bias, unrealistic fill assumptions and omitted transaction costs each independently manufacture returns that do not exist. The system must be engineered so these errors are structurally impossible, not merely avoided by care.
  2. The execution problem. A signal is generated on the index, but the index itself cannot be traded. It must be expressed through a derivative whose price depends on strike, expiry, volatility and time decay. Choosing the wrong contract can destroy a genuine edge — this is invisible to any backtest that stops at the index level.
  3. The reliability problem. The system handles real capital unattended. Network failures, API rate limits, session expiry, partial fills and process restarts are certainties, not edge cases. The system must fail safe rather than fail open.
Design principle

Reaching a well-tested negative result cheaply is a successful outcome. Several components of this project were built specifically to disprove hypotheses, and Section 13 documents a headline claim that was retracted after verification. A system that can only confirm is not a measuring instrument.

04Data Pipeline

Two distinct data paths exist: a request-response path for candles used in trading decisions, and a streaming path used to record order-book depth for the execution-cost measurements in Sections 9.4 and 11.

4.1 Bar construction and the closed-bar rule

The single most dangerous bug in any bar-based system is acting on an incomplete candle. A bar that is still forming has a close price that will change, so a signal computed on it is not reproducible and silently embeds future information. The engine filters every fetched frame to bars whose close time has already passed: 

# only bars whose interval has fully elapsed may influence a decision
now = pd.Timestamp.now(tz=df["date"].dt.tz)
df  = df[df["date"] + pd.Timedelta(minutes=30) <= now].reset_index(drop=True)

4.2 History window sizing

Indicators have warm-up requirements. The daily-EMA-50 trend filter needs at least 50 sessions of history before its value is meaningful, so the daily fetch requests 250 calendar days. An early version requested 30 days; the EMA was computed on insufficient data and returned an unstable value. This class of bug is silent — it produces a number, just the wrong one.

4.3 Session authentication

The broker API issues an access token valid for a single trading day. Both engines read the same token from a shared environment file; requesting a new token invalidates the existing one, so the recorder was explicitly designed to consume credentials it never mints. Credentials live only in a git-ignored environment file and are never logged.

05Signal Generation

Direction comes from a Supertrend indicator confirmed by an exponential moving average. Supertrend is a volatility-adaptive trailing band: it widens in turbulent markets and tightens in calm ones, which makes a single parameter set viable across regimes.

5.1 Average True Range (Wilder smoothing)

True Range captures the full extent of a bar's movement including overnight gaps: 

TR = max( high − low,  |high − prev_close|,  |low − prev_close| )

This is smoothed with Wilder's RMA, not a simple mean. The distinction matters — using the wrong smoother shifts every band and produces different trades: 

def rma(values, n):
    r = np.full(len(values), np.nan)
    r[n-1] = values[:n].mean()                  # seed with an SMA
    for i in range(n, len(values)):
        r[i] = (r[i-1] * (n-1) + values[i]) / n # recursive smoothing
    return r

5.2 The Supertrend band and its state machine

Raw bands are placed at hl2 ± factor × ATR, then made "sticky": a band may only tighten toward price, never loosen, unless price closes through it. Direction is a two-state machine that flips only on a close beyond the opposing band — this hysteresis is what suppresses noise. 

final_upper[i] = upper[i] if (upper[i] < final_upper[i-1]
                            or close[i-1] > final_upper[i-1]) else final_upper[i-1]

# direction: 1 = bearish, −1 = bullish
dir[i] = (−1 if close[i] > final_upper[i-1] else 1)  if dir[i-1] == 1 \
    else (1 if close[i] < final_lower[i-1] else −1)

5.3 Entry condition

A trade requires a direction flip confirmed by price position relative to the EMA. Requiring both conditions filters flips that occur against short-term momentum: 

long_signal  = dir[i] == −1 and dir[i-1] ==  1 and close[i] > ema[i]
short_signal = dir[i] ==  1 and dir[i-1] == −1 and close[i] < ema[i]

06Strategy Logic & Filters

A raw signal is necessary but not sufficient. Six independent filters may veto entry, each motivated by a specific observed failure mode. All are computed only from information available at the decision instant.

6.1 Conditional position sizing

One rule increases size rather than vetoing. When a long signal coincides with a mild five-day pullback (between −2% and 0%), the position doubles to two lots — buying strength that has paused rather than strength that has run. This subset materially outperforms:

 25% of trades generate 69% of profit. The sizing rule identifies a genuinely different population, not merely a leveraged version of the same one.

6.2 Exit logic

Three exits compete, all defined on the index rather than the option price so that behaviour is independent of which contract was chosen: a fixed stop at 1.2%, a target at 3.6% (3:1 reward-to-risk), and a trailing stop at 0.75% from the peak favourable excursion. A reversing signal also closes the position.

07Option Pricing & Contract Selection

The broker API returns option prices but not greeks, so the system computes them. This is the numerical core of the project.

7.1 Black–Scholes and implied volatility

Delta — the sensitivity of option price to a one-point index move — determines how much of the signal's edge the position captures. Because implied volatility is not published, it is recovered from the traded at-the-money price by bisection, exploiting the monotonicity of price in volatility: 

def implied_vol(price, S, K, T, kind):
    lo, hi = 0.01, 4.0
    for _ in range(60):            # 60 halvings → ~1e-18 precision
        mid = (lo + hi) / 2
        if black_scholes(S, K, T, mid, kind) > price: hi = mid
        else:                                        lo = mid
    return (lo + hi) / 2

Bisection is chosen over Newton–Raphson deliberately: it cannot diverge. Newton converges faster but becomes unstable when vega approaches zero — precisely the deep in-the-money region this system trades in. Guaranteed convergence outweighs speed here.

7.2 Strike selection

The selector scores candidate contracts and picks the one whose delta is closest to a 0.95 target, breaking ties by tighter spread then higher open interest. A hard floor rejects anything below delta 0.90.

Empirical refinement — round strikes

Analysis of recorded market depth showed strikes at multiples of 100 carry 2.6× the open interest of their intermediate neighbours and quote ~8% tighter, with multiples of 500 reaching 3.75×. The selector was therefore restricted to multiples of 100. Backtesting showed the constraint costs 0.2% of return — statistically indistinguishable from zero — while eliminating the 48.5% of fills that previously landed on thin strikes. A measurable execution improvement at no meaningful cost.

08Order Execution & Risk Management

8.1 Marketable limit orders

Market orders guarantee execution but not price — dangerous in a thin book where a single order can sweep several levels. The system instead places a marketable limit order: a limit priced just beyond the opposing quote. It fills immediately like a market order under normal conditions, but bounds the worst-case fill. It also survives the case where a strike has not yet traded, which causes some market orders to be rejected outright.

8.2 The shared-account concurrency problem

Two engines trade one broker account. The broker reports only a net position per contract, so if both engines hold the same strike, neither can determine its own share from the API alone. This is a classic shared-mutable-state problem in an environment with no transactions and no locks.

Two naive approaches both fail:

  • Trust the broker's net — engine A closes and sells the entire net quantity, silently liquidating engine B's position.
  • Trust internal state only — after a partial fill or restart the engine's belief diverges from reality and it may sell quantity it does not own, opening an unintended naked short with unbounded risk.

The implemented solution caps every exit at the minimum of both views:

sell(symbol, min(position["qty"], broker_net_quantity))

This is safe in both directions simultaneously: it can never sell more than the engine owns (no accidental naked short), and never more than the broker shows (no liquidating the other engine's leg). It is deliberately conservative — under disagreement it under-sells, leaving a residual position that is detectable and correctable, rather than over-selling into an unbounded liability.

8.3 Failure handling

Session expiry

Token errors are caught per-iteration and logged without terminating the process, so the engine recovers when the token is refreshed rather than requiring a restart.

Network faults

Connection resets are caught at loop level. The loop continues; a transient fault costs one polling cycle, not the session.

Process restart

Position state persists to disk on every transition. A restarted engine reloads its true position instead of assuming it is flat.

Expiry rollover

Positions held into expiry day are closed and reopened in the next series automatically after a fixed cutoff time.

09Backtesting Methodology

This section is the methodological heart of the project. The backtester is engineered to be pessimistic, because an optimistic backtester is worse than none — it produces confident, unfalsifiable, wrong conclusions.

9.1 Realistic gap fills

A naive backtester assumes a stop executes at the stop price. In reality, if the market gaps through the stop overnight, the fill occurs at the open — which may be far worse. The simulator therefore fills at the worse of the two: 

if low[i] <= stop:                       # long stopped out
    exit_price = min(stop, open[i])      # gap-through fills at the open

9.2 Lagged trailing stop

A subtle look-ahead bug: if the trailing stop is updated using the current bar's high before testing that same bar's low, the simulation uses information it could not have had. The peak is therefore updated only after exit evaluation, so the trail always lags by one bar exactly as it would live.

9.3 Complete transaction costs

Every simulated round trip is charged the full regulatory cost stack:

9.4 Measuring the spread rather than assuming it

The spread term dominates the cost stack, so it was measured rather than estimated. Live top-five order-book depth was recorded across six full trading sessions for the option chain around the money, and the resulting samples were grouped by moneyness:

9.5 Independent verification

The strategy was independently reimplemented in Pine Script on TradingView. That platform reported 42,964 points against the Python backtester's 40,740 — agreement within ~5%, with the difference attributable to intrabar fill ordering. Two implementations written against the same specification on different engines agreeing to within 5% is meaningful evidence that neither contains a gross logic error.

9.6 Falsification tests

  • Per-year decomposition — a strategy profitable only in one regime is a curve fit. This one is positive in all seven calendar years.
  • Parameter sensitivity — results must degrade smoothly, not collapse, as parameters move. A sharp peak indicates fitting to noise.
  • Cost stress testing — conclusions were re-derived at 2×, 4× and 8× the measured spread to confirm they do not depend on a favourable cost assumption.
  • Component ablation — each filter was tested independently to confirm it contributes, rather than being carried by the others.

11Research Study — Which Contract to Buy

All results above are expressed in index points. But the index cannot be traded directly, and the choice of option contract determines how much of that theoretical edge survives. This study re-prices all 724 historical trades under different contract choices, holding signals, entries and exits fixed so that only the execution vehicle varies.

11.1 Why the intuitive choice fails

Delta capture

Measured across all trades, the deep-ITM position converts 0.96 of every rupee of index movement into P&L; the ATM contract converts 0.49. The strategy's edge is defined in index points, so halving delta halves the gross return.

Time decay

Mean holding period is 1.6 days with 156 expiry rollovers. Deep-ITM premium is almost entirely intrinsic value and barely decays; ATM premium is entirely time value and bleeds every night the position is held.

Asymmetric loss profile

118 ATM trades lost more than 80% of premium, against 23 for deep ITM. Small index winners become option losers once decay is paid — which is why win rate collapses from 41.9% to 31.5%.

Liquidity is not the counterargument

Deep-ITM spreads are wider in absolute points but narrower as a share of premium (0.25% vs 0.31%). Measured on the real book, the intuitive liquidity objection does not hold.

The conclusion is robust to cost assumptions: even charging deep-ITM contracts eight times the measured spread, they still outperform ATM by ₹6.2 lakh. The result also holds in every single calendar year — ATM never wins once in seven years.

Why this matters methodologically

A price-only backtest would rate every one of these variants identically, because the signals are the same. The entire ₹12 lakh difference lives in the execution layer that conventional backtesting ignores. This is the project's central research finding: for derivatives, how a signal is expressed can matter more than the signal itself.

12Engineering Problems & Solutions

12.1 An inverted timestamp convention

The time-of-day filter compared against a timestamp representing each bar's close, while the specification was written in terms of bar start. The filter was therefore shifted by one full bar: it excluded 09:45 while admitting the intended exclusions incorrectly. The system ran, produced trades and logged no errors — the bug was visible only by reconciling live trades against backtest trades one by one. It is a reminder that in time-series systems the most dangerous defects are semantic, not syntactic.

12.2 Percentage buffers on large premiums

The order buffer was specified as a percentage of price. On a low-premium contract this is a few paise; on a deep-ITM contract priced at 434 points it authorises over 2 points of slippage — against a measured requirement of 0.62. The parameter scaled in exactly the wrong direction relative to risk. Identified by comparing the buffer against recorded book depth; the fix is an absolute cap applied to entries.

12.3 Deployment safety procedure

Because deployment touches a system holding real capital, each release follows a fixed sequence: verify the engine is flat → back up the current binary with a timestamp → upload alongside, never overwriting → byte-compile on the target host and abort if compilation fails → atomically swap → restart → verify service state, restart count and error log → confirm the startup banner reports the expected configuration.

Compiling before swapping is the critical step: a syntax error discovered after overwriting leaves an unstartable engine, whereas discovering it beforehand costs nothing. Deployments are scheduled outside market hours whenever possible.

12.4 Validating a rewrite against its predecessor

When the decision logic was rewritten, correctness was established by replaying both implementations over 1,408 historical signals and comparing outputs. Agreement was 99.72%; all four disagreements traced to an early-2020 warm-up window where insufficient history existed for a stable EMA — a condition that cannot occur live, since the engine always requests 250 days. Steady-state agreement was therefore 100%. Differential testing of this kind is far stronger evidence than unit tests written by the same author as the code.

13Scientific Integrity — A Withdrawn Result

Retracted finding

An earlier version of the execution study concluded that index futures outperformed all option variants, reporting ₹2,301,473 at a Sharpe of 2.22. That result was withdrawn before final submission. It is documented here rather than deleted, because how a result fails is part of the result.

No historical futures price series was available, so futures profit and loss had been approximated as index profit and loss minus a flat cost — implicitly assuming futures track the index one-for-one. Testing that assumption against the recorded order-book data showed it to be badly wrong:

SessionIndex moveFutures moveDivergence
14 July 2026−45.10−81.6036.5 pts
21 July 2026−39.90−62.3022.4 pts
 Both feeds tick every second and 100% of futures ticks matched an index tick, so the divergence is genuine basis behaviour rather than a timestamp-alignment artifact.

Against an average trade gross of 123 index points, a 22–37 point per-session divergence represents 18–30% of an entire trade, while the flat carry charge modelled only 2–3 points. Both observations moved against a long position, and the strategy is 80% long — so the error was very likely flattering the withdrawn result. Since the strategy trades index-derived signals priced against the same index, the option comparison is unaffected; only the futures row depended on the unverifiable proxy, and only that row was removed.

The methodological lesson: never rank an instrument for which no price history exists. A flat cost deduction cannot substitute for the dynamics of an unobserved series. The failure was caught by challenging a convenient assumption after the result was already written up — which is precisely when such challenges are least welcome and most necessary.

15Limitations

  1. Synthetic option pricing. Historical option prices were not available, so the study prices contracts with Black–Scholes using India VIX as the volatility input. This ignores volatility skew. The effect is small for deep-ITM contracts (near-zero vega) but real at the money.
  2. Narrow execution-cost sample. Six recorded sessions is sufficient to characterise the spread ladder but not to capture rare stress conditions, where liquidity behaves very differently.
  3. Measured strikes do not cover traded strikes. Depth was recorded ±350 points around the money, reaching delta 0.877, whereas the engine trades delta 0.95. Deep-ITM liquidity figures are therefore extrapolated rather than directly observed.
  4. Single instrument. All results concern NIFTY options. Generalisation to other underlyings is untested and should not be assumed.
  5. Backtest-to-live gap. Historical simulation cannot fully capture queue position, partial fills or the market impact of the system's own orders.
  6. Survivorship of the research process. Many parameter combinations were examined before settling on the final configuration. Out-of-sample and cross-platform verification mitigate this, but forward performance should be expected to be somewhat below backtested performance.

16Future Work

Widen depth recording

Record depth out to ±800 points so the strikes actually traded are directly measured rather than extrapolated — converting the largest stated limitation into an observation.

Absolute slippage cap

Replace the percentage order buffer with an absolute point cap on entries, sized from the measured requirement.

Learned execution timing

Use the recorded book to train a short-horizon model that defers entry by seconds when the book is unusually thin — a natural extension of the microstructure dataset.

Live-versus-backtest telemetry

Systematically log realised slippage per fill and compare against the model, so the cost assumption is continuously re-validated in production.

Portfolio-level risk control

A supervisory process enforcing an account-wide daily loss limit and kill switch across both engines, rather than per-engine limits.

Volatility surface modelling

Replace the single VIX input with a fitted skew surface to improve pricing accuracy for near-the-money contracts.

17Conclusion

This project delivers a complete, operational algorithmic trading system rather than a simulation exercise. It ingests live market data, computes derivative pricing models numerically, selects contracts on measured liquidity criteria, manages order lifecycle and failure recovery, and runs unattended on a cloud host — with two independent engines safely sharing a single broker account.

The strategy achieves a profit factor of 2.08 across 735 trades and 6.5 years, profitable in every calendar year tested, and cross-validated against an independent platform implementation to within 5%.

The more transferable contribution is methodological. The execution study demonstrates that a signal's theoretical edge and its realisable edge are different quantities, separated by a factor of more than two depending on an implementation choice invisible to conventional backtesting. Measuring that gap required capturing live order-book data purely to answer the question empirically rather than by assumption. And Section 13 shows the same evidence being turned against the project's own conclusions — retracting a favourable result once its foundational assumption failed verification.

Building a system that produces a profitable backtest is straightforward. Building one whose results can be trusted — engineered so the common self-deceptions are structurally impossible, and willing to reject its own findings — is the substance of the work.

Note on reproducibility. All performance figures derive from historical simulation over 2020–2026 NIFTY data with complete transaction costs applied. Backtested results do not guarantee future performance. Live deployment operates with capital at risk under the author's supervision.

Note on security. No API keys, access tokens, host addresses or account identifiers appear in this document or in any committed source file. Credentials are held solely in environment files excluded from version control and are never written to logs.
